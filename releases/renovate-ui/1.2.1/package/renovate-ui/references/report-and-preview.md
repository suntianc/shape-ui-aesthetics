# Report and Preview

Renovation earns its mandate by showing the destination before touching anything. Two artifacts, delivered together, before any product code changes.

## The analysis report

One document, written for the product owner, in this order:

1. **Verdict first.** The grade, one sentence of why, and what the mandate authorizes and protects. The owner should be able to stop reading after this paragraph and still decide.
2. **Evidence by domain.** For each domain lens that produced material findings: the observation, the measured value where one exists, and the capture that shows it. Measured findings cite the band they violate and the reference sites behind that band ("body 13px/1.3 against a reading band of 1.4–1.75 measured from pudding.cool, ia.net…"). Skip quiet domains; a padded report reads as taste, and taste is refusable.
3. **The change plan.** What changes at this grade, surface by surface; what is explicitly preserved; what was noticed but deferred to a future cycle (with its honest grade).
4. **Risk and reversibility.** What the renovation touches that is hard to undo, and how the work is staged so the owner can stop between stages.

Write in the owner's language, not the skill's: no internal jargon (domain-lens names, recipe IDs) without a plain-language gloss.

## The preview

One self-contained HTML page proving what the renovated interface will look like — the strongest anti-anchoring instrument this workflow has, because it lets the owner compare futures instead of imagining them.

- **Real content only.** The product's actual copy, data, and imagery. A preview with lorem ipsum or invented features is a mood board, and mood boards get polite nods instead of mandates.
- **A consequential surface.** Preview the screen where the grade's consequences are most visible — the dashboard for a Rebuild of a tool, the article page for a reading product — not the easiest screen to make pretty.
- **Shippable fidelity.** Responsive, real states where they matter, honest typography and spacing. The preview is held to the same aesthetic bar as a delivered page; it *is* the audition for the whole renovation.
- **Apps preview in a frame.** For mobile or desktop apps, render the surface as a high-fidelity mockup inside a device frame at native proportions. State plainly that the preview is a visual promise to be implemented in the product's real stack — not a claim that the HTML is the implementation.
- **Before/after, side by side.** Pair the preview with the current capture of the same surface. The comparison is the argument; let it do the persuading.

## The mandate conversation

Present report and preview, then ask for the mandate explicitly. Three outcomes:

- **Accepted** — execution proceeds at the graded mandate.
- **Bounded** — the owner accepts the diagnosis but authorizes less ("Rebuild is right, but this cycle is Calibrate only"). Record both the honest grade and the bounded mandate; execute within the bound.
- **Contested** — the owner disputes the diagnosis. Return to evidence: which finding is wrong, or which product truth (brand constraint, audience fact) was missing from the evidence set. Regrade honestly if the evidence changes; do not regrade to be agreeable.

Execution without one of these three recorded outcomes is a protocol violation — exactly the unauthorized timid-or-reckless middle ground this skill exists to eliminate.
